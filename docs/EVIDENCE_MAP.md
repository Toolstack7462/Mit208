# Evidence map

Every claim the report makes, against the file that supports it and the command that
checks it.

This was Appendix A of the report until the appendices were reduced to the evidence
the marking rubric asks for. It is marker-facing scaffolding rather than academic
argument, so it is kept here instead: useful for verifying the submission, not part
of it.

| Report claim | Repository evidence | How to verify it |
|---|---|---|
| Core analyst and staff workflow completes end to end | `backend/app/routers/`, `frontend/src/pages/`, 175 backend and 92 frontend tests | Run `backend/smoke_test.py` against a running server: 22 of 22 checks |
| Architecture and data flow are as described | `docs/ARCHITECTURE.md`, `docs/ERD.md`, `evidence/make_architecture_figure.py` | Every box in Figure 1 names a file that exists at that path |
| Rules are enforced by the server, not the interface | `app/transitions.py`, `app/deps.py`, `app/schemas.py`, database `CHECK` constraints | `backend/tests/test_transitions.py` and `test_security.py` |
| The interface offers only valid actions | `frontend/src/lib/transitions.js`, `components/EmailDetailPanel.jsx` | `test_transitions.py` asserts the mirror matches the Python table |
| The templated-language flag does not claim authorship detection | `app/scoring.py` `TEMPLATED_PHRASES` | Twelve stock phrases, matched as substrings; the badge reads "Templated Language" |
| bcrypt's 72-byte limit is enforced at the API boundary | `app/schemas.py` password validator, `app/security.py` | `test_security.py` multi-byte password cases |
| Every login is recorded | `app/routers/auth.py` — both `/login` and `/token` write an audit row | `test_security.py::test_the_oauth2_token_route_is_audited_like_login` |
| The audit trail is append-only at application level | `app/audit.py`, `routers/audit.py` | No route updates or deletes a row; `docs/SECURITY.md` states the limit |
| Problems were investigated, not just patched | `docs/BUG_LOG.md` — 18 entries, each with a named regression test | Appendix C of the report extracts the four most significant |
| No credential is published | `evidence/secret_scan.py`, `.gitignore`, `backend/.env.example` | The `secrets` job fails the build on any finding |
| The prototype is reproducible | `README.md`, `requirements.txt`, `package.json`, `database/schema.sql`, seed data | Follow README setup; CI performs the same steps from scratch |
| The API version is distinct from the release tag | `backend/app/__init__.py` `__version__` | `test_security.py::test_the_api_reports_one_centralised_version` |

## Figure and screenshot provenance

The report's captions cite "Author, based on the implemented PhishGuard system" or
"Author's screenshot of the running application", which is the academic convention.
The generating scripts are recorded here instead:

| Report figure | Generated by | Source data |
|---|---|---|
| Figure 1, architecture | `evidence/make_architecture_figure.py` | Hand-maintained layer definition, cross-checked against the files it names |
| Figure 2, data model | `evidence/make_erd_figure.py` | Cross-checked against `app/models.py` at generation time; the script fails if a drawn column no longer exists |
| Figure 3, core workflow | `evidence/make_workflow_figure.py` | Crops of screenshots 04, 06, 11 and 14 |
| Appendix D, CI and release | `evidence/capture_ci_evidence.py` | GitHub Actions API; refuses to run unless the run passed |
| Appendix E, interface evidence | `evidence/capture_screenshots.py` | Playwright against the running application at 3200 x 2000 |

`evidence/screenshots/INDEX.md` is generated by the capture scripts and describes
every image, including which database engine served it.
